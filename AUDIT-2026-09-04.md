# Slopbot audit and UI improvements — September 4, 2026

Release: **1.8.1**. Audited baseline: **891fe12**, fetched from main before editing.

## Why the UI changed

The recent all-time-streak/event-notification work replaced `_update_leaderboard`'s full standings
embed with individual `leaderboard_movement` events sent by a generic notifier. A single swap
therefore produced two cards, each repeating the heading, timestamp, and playlist. The supplied
screenshot shows four such cards where the older presentation used one complete board.

The repair restores that compact presentation while keeping the newer event ledger and permanent
streak tracking. It does not revert the all-time-streak feature.

## Changes

| Area | Result |
| --- | --- |
| Leaderboard announcements | One standings card per observed playlist ordering change. Shows position, player, MMR, and movement arrows, including unchanged players. One observation timestamp per card. |
| Delivery persistence | Saves the standings text with the update. A retry after a newer poll or restart still uses the original numbers. Per-player movements remain in `/today` without generating duplicate cards for the same update. |
| Names and large boards | Escapes mentions and Markdown, flattens line breaks, bounds displayed names and card size, and explicitly reports omitted players above the display limit. |
| Equal MMR | Uses the same display-name and account-ID tiebreak ordering as `/leaderboard`. |
| Command responsiveness | Applies the existing bounded policy-lookup/defer helper to all 13 shareable result handlers. Slow database access no longer delays their first acknowledgement indefinitely. Fast access denials stay private. |
| Activity history | Long `/today` results use Previous/Next controls and a page count in one message. The caller owns the controls; they last five minutes. |
| Player dashboard | Acknowledges graph selections before database/chart work and shows the selected section in the dropdown. |
| MMR charts | Larger text, fitted titles, separated date/summary lines, and UTC time labels for same-day sessions. Rendered and visually checked. |
| Deployment | Version bump, documented backup/update/smoke-check/rollback procedure, and updated README behavior. |

## Audit coverage

Reviewed the Python modules and test coverage for voice alerts, visibility policies, account
resolution, event storage and delivery, history/leaderboard formatting, item-shop watches,
tournaments, scheduled requests, Telegram routing, status workers, configuration, and startup.
Also inspected the Go API boundaries, request validation, loopback binding, authentication/token
handling, and systemd deployment units, and ran the Go tests and vet.

The existing checks cover guild/user isolation, inaccessible-channel filtering, opt-outs, deduplication,
retry behavior, migrations, conservative match inference, permanent streak semantics, and command
catalog coverage. These protections remain in place. No new service, package dependency, command,
permission, or configuration flow was introduced. No credentials or production database were needed.

## Validation

- **222 Python tests passed** (202 baseline tests plus 20 new cases), with Ruff lint/format checks
  and strict mypy passing. The only test warning is discord.py's existing `audioop` deprecation.
- Added regression coverage for a six-player standings change, quiet baseline and same-order MMR
  changes, failed-send retry, restart persistence, absence of duplicate movement cards, large/unusual
  names, and guild/playlist/poll isolation of summary suppression.
- Exercised all 13 result handlers under slow access-policy denial, plus private fast denial.
- Tested dashboard acknowledgement/selection and pagination ownership, page boundaries, and
  delivery of all 100 requested activity events through one message.
- Go `test ./...` and `vet ./...` pass with the pinned dependencies.
- Generated and inspected the actual chart PNG; corrected label overlap found in the first render.

## Scope and remaining limits

No live Discord/Rocket League session or Raspberry Pi deployment was performed. The deployment guide
includes those final smoke checks. This is a code and regression audit, not a production load test
or a dependency-vulnerability certification; dependencies and the Go protocol integration were not
upgraded speculatively.

Cards apply to newly observed updates. Already posted Discord messages are untouched, and older
queued movements keep their legacy format. A large notification backlog still drains through the
existing bounded queue. As before, a process crash after Discord accepts a message but before its
delivery receipt is saved can lead to a retry; Discord delivery and SQLite are not one transaction.

See [deployment and rollback instructions](deploy/UPDATE-1.8.1.md).
