# Slopbot reliability audit — September 5, 2026

Version **1.8.2**. Baseline: **0b03ec7**, checked against freshly fetched `origin/main`.
The fetch confirmed local main and GitHub main were identical. In-progress work was preserved;
no reset, forced checkout, or force push was needed.

This pass prioritizes demonstrated correctness problems beyond the prior UI audit. It adds no
commands, product features, services, permissions, or dependency upgrades.

## Verified fixes

| Problem | Fix and evidence |
| --- | --- |
| Cancelling a database call released the store lock even though its SQLite thread continued running. A second operation could enter concurrently, breaking the store's serialization guarantee. | Keep the lock until the underlying worker has exited, then propagate cancellation. Tests cover repeated cancellation and an error in the cancelled worker. |
| A missing guild/member cache entry could permanently delete personal tournament settings or finish an undelivered one-time reminder. | Fetch uncached members. Only confirmed Not Found removes membership-dependent state. Missing guilds, Forbidden, and HTTP failures remain retryable; one-time retries keep the existing bounds. Tests cover cache recovery, outages, actual departures, and retry exhaustion. |
| Claiming an admin-added Epic account transferred matches and streaks but left MMR history and peak rows under its negative unlinked ID. | Transfer those rows in the existing claim transaction. Startup also repairs older affected rows only when the same player has a linked account in the same guild. Tests preserve the MMR values and special-mode match history, and verify repeatable repair. |
| `/movers` shortlisted the top 20 absolute changes before separating gains/losses and filtering departed members. A busy server could show no fallers despite recorded losses. | Apply display limits after eligibility and direction selection. The store's default bounded query behavior is retained for other callers. A 22-player regression verifies both directions. |
| `/slopbotstatus` could return a snapshot from the ten-minute background poll after health had changed. | Explicit status requests collect fresh health. Background state-change notification behavior stays unchanged. A regression verifies a cached healthy state cannot hide a current failure. |
| Leaderboard snapshot replacement committed before event insertion. An insertion failure could erase the change from the next poll's comparison and lose its announcement. | Commit changed standings and their events together. A SQLite trigger simulates failure partway through insertion: neither events nor the new snapshot survive; the next poll records the change once. |

## Durable workflow safeguard

The new root [AGENTS.md](AGENTS.md) requires agents to fetch/check main before work and again before
integration/push, preserve dirty and unrelated changes, fast-forward clean main safely, and handle
divergence without discarding commits or force-pushing. A blocked fetch must be disclosed. This is
a per-task instruction, not an automatic background pull that might disrupt active work.

## Validation

- **234 Python tests passed**: 222 existing cases plus 12 new reliability cases.
- `ruff check .`, `ruff format --check .`, and strict `mypy src` passed.
- Go `test ./...` and `vet ./...` passed with the existing pinned dependencies.
- `git diff --check` passed.
- The only Python warning is discord.py's existing `audioop` deprecation.

Tests use local SQLite and mocked external delivery. They do not send Discord/Telegram messages or
access a production database. No resets were redeemed. The account-shared usage allowance was
checked at phase boundaries with an 80%-used stop threshold; it is a best-effort guard rather than
an enforceable billing cap.

## Remaining verification and limits

- Live Raspberry Pi deployment and real Discord/Telegram/Rocket League smoke checks remain for the
  operator. There was no deployment in this audit.
- Production-scale load, prolonged reconnect/rate-limit scenarios, exhaustive payload-size fuzzing
  across every command, and external dependency-vulnerability scanning were not performed.
- Discord sending and SQLite receipt storage still cannot commit as one transaction. A crash after
  a successful external send but before its receipt can cause a duplicate retry. The fix above
  addresses the separate, reproducible event-loss window during local leaderboard persistence.
- Automatic repair covers stale MMR ownership where a matching current link exists. It cannot
  reconstruct history that a prior version or an operator already deleted.

## Updating an existing 1.8.1 installation

Use the backup-and-update procedure in [the deployment guide](deploy/UPDATE-1.8.1.md): fetch/pull
main safely, stop Slopbot, back up SQLite, reinstall the Python package, and restart Slopbot. No Go
rebuild or environment changes are needed for this Python-only release. Startup repairs affected
ownership rows without resetting preferences, ranks, history, or streaks. The pre-update application
revision for this release is `0b03ec7` if rollback is necessary; retain the live database.

After restart, run `/slopbotstatus`, inspect `/movers`, verify an Epic-account claim retains its
MMR/peak ownership, and confirm configured tournament reminders still work. The existing compact
leaderboard UI and special-mode match history are preserved.
